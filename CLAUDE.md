# LedgeEaze

A shared personal finance tracker (PWA). Multiple users can see each other's transactions once they approve access to each other; budgets, goals, and personal details stay private per-user.

- **Live:** https://finance-tracker.rohith24112.workers.dev
- **Stack:** React 18 + Vite + TypeScript + Tailwind + TanStack Query + React Router v6 + Recharts + lucide-react + dnd-kit
- **Backend:** Supabase (Postgres, Auth, Storage, RLS) — project id `izidxazhknyoxeqgnqdb`
- **Hosting:** Cloudflare Workers (static assets), deployed via `npm run deploy` (`wrangler` is a pinned exact-version devDependency, not fetched fresh by `npx` each time)
- **Admin:** role-based via the `admin_users` table + `is_admin()` (currently one admin, `rohith24112@gmail.com`; see RLS / access patterns below)

## Product standards (from the user -- apply to every change)

- **iPhone first, then everything else.** Design and check every screen on an iPhone-sized home-screen PWA first (375-390px wide, `--safe-top` set to ~69px to mimic the notch, bottom tab bar present, iOS quirks: no backdrop blur on fixed bars, `MonthField` instead of native month/date wheels, 16px inputs so iOS doesn't zoom, no sticky :hover after a tap). Only then check tablet and desktop. The user uses the app mostly on an iPhone.
- **Plain, simple words in the UI.** Write copy a non-finance person gets at a glance: "Not enough money in HDFC Bank" (not "insufficient balance" or "shortfall"), "Paid", "Due Oct 5", "Money in / Money out". Short sentences, no jargon, no internal terms (fingerprint, RPC, opening balance -> "balance today"). Warnings say what is wrong and what to do ("Update balance").


Standard workflow after a batch of changes: `npm run check` (or at minimum `npx tsc -b`) → commit → push → `npm run deploy`. `.github/workflows/ci.yml` runs `npm run check` on every push/PR to `main` as a validation gate — but it only checks, it doesn't deploy; deployment is still a manual `npm run deploy` from someone's machine.

**Security regression tests:** `supabase/tests/security_regression.sql` re-asserts every access rule (no anon EXECUTE on SECURITY DEFINER functions, RLS on every public table, `admin_users` unreachable, profiles/transactions/feedback/private tables scoped correctly for QA15, admin sees all via `is_admin()`, a spoofed admin-email claim grants nothing, anon reads nothing, the transfer/FX CHECK constraints, debit cards own-only and the debit-card/transaction consistency trigger). It impersonates roles inside one transaction and **rolls back**, raising on the first failure — run the whole file via the SQL editor or `execute_sql` after any migration touching RLS, grants or functions; expect a single `ALL SECURITY CHECKS PASSED` row. It isn't in CI (CI has no database credentials).

## Database

- `supabase/schema.sql` — hand-maintained, **append-only** DDL. Represents what a fresh install would run top to bottom. When schema drifts from a migration (see Postgres gotcha below), append a correcting `alter table` block rather than editing the original `create table` in place.
- `supabase/policies.sql` — hand-maintained, the actual RLS source of truth, kept separate from schema.sql.
- Both files must be kept in sync by hand with every migration applied via `mcp__supabase__apply_migration`. There is no automatic schema dump/diff step — if you apply a migration, edit both files in the same batch.
- Every user-owned table has an `owner_user_id uuid references auth.users(id) on delete cascade` column. Deleting an account (`delete_own_account()` RPC) relies entirely on these cascades.

### Known Postgres gotcha: `on delete` clause drift

`categories`, `accounts`, and `tags` each have a `created_by` FK to `auth.users`. The live constraints were found to be missing `on delete set null` even though `schema.sql`'s `create table` statements document it — meaning any account that had ever added its own custom account/category/tag could not delete itself (the `created_by` FK blocked the cascade after every other row had already succeeded, rolling the whole delete back). Fixed via `fix_created_by_fkey_delete_action_drift`. **Lesson:** don't trust `schema.sql` as ground truth for `on delete` behavior — verify live constraint definitions with:
```sql
select conname, conrelid::regclass, pg_get_constraintdef(oid)
from pg_constraint where confrelid = 'auth.users'::regclass and contype = 'f';
```

### RLS / access patterns

- **Admin is a role, not an email.** `public.admin_users(user_id)` lists admins; `public.is_admin()` (SECURITY DEFINER, stable, authenticated-only EXECUTE) is what every admin RLS policy calls (`feedback_select_admin`, `feedback_update_admin_reply`, `profiles_select_own_or_connected`), and the client mirrors it with `useIsAdmin()` (`src/lib/admin.ts`, calls the same RPC — UI only, RLS enforces). `admin_users` has RLS on, no policies and no grants, so it isn't readable or writable through the API directly. **Since 1.12.0 (owner's request) admins can be added/removed from the Admin page** -- only through `admin_grant_admin(p_user)` / `admin_revoke_admin(p_user)` (SECURITY DEFINER, 42501 unless `is_admin()`, the last admin can't be removed). This reverses the earlier SQL-editor-only rule; it is a privilege-escalation surface by nature, so every admin action is logged (see Admin actions below). This replaced `auth.jwt() ->> 'email' = 'rohith24112@gmail.com'` checks (and an `ADMIN_EMAIL` client constant) that had to be kept in sync by hand.
- **Admin dashboard (`/admin`, `AdminPage.tsx`, reached from the profile menu when `useIsAdmin()`; `useAdminStatus()` gives the loading state so the route doesn't bounce before the answer)**: Overview, Users, Feedback (the bell's `AdminFeedbackInbox` with an open/replied `filter`), Errors and Announcements. Data only through `admin_overview()`, `admin_list_users()` and `admin_client_errors(p_days)` (migration `2026-09-29_admin_dashboard.sql`) -- SECURITY DEFINER, `search_path = ''`, each raising 42501 unless `public.is_admin()`, authenticated-only. They return counts and account info (sign-up/sign-in times, setup done, entry counts), **never anyone's transactions, amounts or budgets** -- keep it that way. `client_errors.app_version` (sent by `logClientError` from `APP_VERSION`) lets errors group by release. `app_announcements`: RLS -- everyone signed in reads live ones (active, before `ends_at`), only `is_admin()` writes; `AnnouncementBanner` (AppShell) shows the newest live one, dismissed per browser in localStorage. `user_settings.setup_checklist_dismissed` is for the Home setup checklist. The security suite covers all of it (non-admin refused, anon nothing). Testing the page needs an admin session -- granting QA15 admin was (rightly) blocked; the real admin account must not be used for mutating tests.
- **Admin actions (Users tab, `AdminUserActions.tsx`; migration `2026-09-30_admin_actions.sql`)**: Send password reset (Supabase Auth `resetPasswordForEmail` from the admin's browser, then `admin_note_reset_sent` logs it), Make/Remove admin, Delete account (`admin_delete_user`: not yourself, not an admin -- remove the role first; type the email to confirm; deletes `auth.users` so every owner_user_id cascade runs, like `delete_own_account`, **but their storage files (receipts, avatar) are not removed** -- only the owner can delete their own folder). Every action is written to `admin_audit` (RLS on, no grants) via the no-EXECUTE helper `admin_log`, and shown as "Recent admin actions" through `admin_audit_log(p_limit)`. The security suite checks non-admins are refused and the log is unreachable.
- **Share with everyone, per entry** (`transactions.shared`, default true; migration `2026-09-30_transaction_sharing.sql`): the New entry sheet has a "Share with everyone" tick (on by default; editing shows the entry's setting). Unticked, approved viewers don't see the entry, nor a receipt attached to it -- `transactions_select_own_or_approved`, `documents_select_shared` and the `documents_storage_select_shared` storage policy all require `shared` for the viewer branch. The owner always sees it; Activity marks it with a small lock ("Only you can see this"). Totals, budgets and exports for the owner are unchanged; a viewer's Everyone view simply doesn't include it.
- **New-user setup**: a 4-step welcome wizard (You -> `BanksStep` -> `AccountsStep` titled "Cards and wallets" -> Salary, `SalarySettings bare`), then Home's `SetupChecklist` (accounts, salary, bills, budget, goal, import, share; done-ness derived from data by `setupChecklist` in `src/lib/setupChecklist.ts`, tested). **Walkthrough after an update:** each step has a `SINCE` version; hiding the card stores `user_settings.setup_checklist_version = SETUP_CHECKLIST_VERSION`, and a hidden card comes back (new steps tagged "New") only while a step added after that version isn't done. **Adding a step = give it the next `SINCE` number and bump `SETUP_CHECKLIST_VERSION`.** `BanksStep` picks the user's banks from the signup seed list and carries out `planBankSetup` (`src/lib/bankSetup.ts`, tested): adopt picked seeds as the user's own, add typed ones, update in-use ones, and **delete the untouched seeds not picked** (`useRemoveAccounts`, one `.in()` delete -- never an account in use). `BillPicksModal` opens `RecurringFormModal` with `prefill`; `BudgetSuggestionsModal` uses `suggestBudgets` (`src/lib/budgetSuggestions.ts`, tested: top categories of the last 3 full months, limit 10% over, rounded).
- **Salary day** (`user_settings.salary_amount/_account/_day/_confirmed_month`, all-or-none check): Settings -> Salary (`SalarySettings`); from pay day each month Home shows `SalaryPrompt` (`salaryPromptDue` in `src/lib/salary.ts`, tested; a 31st clamps to short months). The form has a **"Last day of the month"** chip (stores 31 = `LAST_DAY`, shown as "the last day of each month" via `payDayLabel`; `shortMonthNote` explains 29-31), and Save shows "Saved" and stays disabled until something changes. Yes logs income (category Salary, tag `#salary`, `allowDuplicate`) and sets `salary_confirmed_month`; an income tagged #salary logged any other way also counts; Not yet snoozes for the day (localStorage). No push -- it's asked when the app is opened.
- **Card networks**: `accounts.card_network` (credit cards only, check-constrained; set via the narrow `set_card_network` RPC -- `set_account_details` clears it when an account stops being a card) and `debit_cards.network` (column-granted). `CardNetworkPicker` in `AccountForm` / `DebitCardForm`. **Payment mode narrows accounts** (`accountsForMode` + `modeUsesDebitCards` in `src/lib/cardNetworks.ts`, tested): "Cash" -> cash accounts (Add entry hides the account chips entirely when there's one cash account); "Wallet" -> wallets only; "Credit card" -> credit cards only; "Debit card" -> just the debit card chips (banks only if there are no cards); "UPI" -> banks, wallets and **RuPay** credit cards (not cash); "Net banking"/"Cheque"/"NEFT" -> banks; no mode or "Other" -> everything, both card rows included. Debit cards are offered only with no mode, "Debit card" or "Other". Picking the cash account sets the mode to Cash (it's stored now -- it used to be cleared), a wallet with no mode gets "Wallet", a credit card gets "Credit card"; switching to "Debit card" picks a card (the one on the current account, else the most recent). `'Wallet'` was added to `transactions_payment_method_check` (migration `2026-09-29_wallet_payment_mode.sql`) and the `PaymentMethod` type. Used by Add entry's chips and Activity's Account filter. `PAYMENT_METHODS` lives there too.
- **Edit sheets save/delete from the header**: `Modal`'s `headerActions` + `SheetSaveButton` (submits a form by id via the `form` attribute, or calls onClick) / `SheetDeleteButton`, left of X -- no Cancel/Save/Remove footer (X is cancel). Used by Accounts & cards (`AccountForm`/`DebitCardForm` with `formId` + `hideActions`), Recurring, Budget, Goal and Rule sheets (delete via the page's existing confirm). Add entry keeps its big Save. Confirm dialogs keep their buttons.
- **Tags can be deleted** everywhere: `delete_tag(p_tag)` (SECURITY INVOKER, own rows via RLS) strips it from the user's transactions and deletes it from `tags`; from Rules -> Tags (confirm) and Add entry's tag "Edit" mode (inline confirm). **Categories**: "+ New" (`QuickAddCategory`) in Add entry's chip row and under the Recurring/Budget category pickers (this replaces the old "no inline add" rule); Settings -> Categories has **Move entries** (`useMoveCategory`: transactions + recurring items, and the budget when the target has none; optional delete of the old category). `MonthField` replaces `<input type="month">` (iOS wheel). Activity filters: Type, Category, Account, **Mode** (server-side `payment_method` filter, in saved views) as a 2x2 grid; Type narrows Category, Mode narrows Account. Add entry's "like last time" chip (`suggestEntry` in `src/lib/smartCategory.ts`, tested) offers category + latest account/card/mode + a repeated amount.
- **Narrow SECURITY DEFINER RPCs** (e.g. `mark_feedback_reply_seen`, `delete_own_account`) are used instead of a broad "user can update their own row" policy, specifically to avoid letting a user edit fields they shouldn't (e.g. their own feedback message once an admin has replied to it).
- Postgres grants `EXECUTE` to `PUBLIC` by default on function creation, **and Supabase additionally grants it to `anon` and `authenticated` explicitly** (visible in `proacl` as `anon=X`) — so `revoke execute ... from public` alone does *not* lock a function down (this was believed done for a while; the security advisor and `has_function_privilege('anon', oid, 'execute')` showed otherwise). Every SECURITY DEFINER function needs `revoke execute ... from public, anon` (and `authenticated` too for trigger/event-trigger functions, which are never RPCs — Postgres only checks EXECUTE on a trigger function at `CREATE TRIGGER` time, not when it fires). Verify a new function with `select has_function_privilege('anon', 'public.fn(args)', 'execute')`. Current state: `delete_own_account`/`mark_feedback_reply_seen`/`find_profile_by_email`/`request_viewer_access`/`mark_recurring_item_paid`/`set_account_opening_balance`/`set_account_details`/`convert_account_to_debit_card`/`is_admin` are authenticated-only; `handle_new_user`/`handle_user_email_update`/`rls_auto_enable` are callable by no one (triggers still fire — signup re-verified after the revoke).
- **Shared-viewer pattern**: `viewer_access` (status = `'approved'`) is joined against in RLS policies to let an approved viewer read another user's transactions/receipts. When adding a new user-owned resource that should be visible to approved viewers (e.g. `documents`, `storage.objects`), mirror `transactions_select_own_or_approved` — remember storage bucket policies are separate from table policies (a document row being readable doesn't mean its file bytes are). Shared documents are only those attached as a receipt to a transaction the viewer can see. **`debit_cards` deliberately does *not* follow this pattern** — it's own-only, so a viewer sees a shared debit-card transaction's `debit_card_id` but can't resolve its name; UI falls back to the account.
- **`profiles` is NOT a readable user directory.** The `profiles_select_own_or_connected` policy lets you read your own row, anyone you share a `viewer_access` row with (either direction, *any* status — so incoming/outgoing/pending requests and shared-transaction owners all resolve to names), and admins (everyone, via `is_admin()`). It used to be `profiles_select_all` (any signed-in user could list every name/email/avatar). Split partners (`transaction_splits`, either side) can also read each other's profile. `profiles.email` isn't user-writable (column grants allow only `display_name`/`avatar`); it mirrors `auth.users.email`. Access requests are created only through the **`request_viewer_access(p_email)`** RPC (exact email; `viewer_access` has no INSERT grant and only `status`/`responded_at` are updatable), so nobody can create a request — and thereby read a profile — from a bare user id. The avatars bucket can't be listed except for your own folder. Consequences: (1) finding someone new in Settings → Sharing goes through the **`find_profile_by_email(p_email)`** SECURITY DEFINER RPC — an *exact*, case-insensitive email match only (no name search, no prefix match, can't return yourself), `revoke`d from `public`/`anon`, `grant`ed to `authenticated`; don't turn it into a prefix/name search or you've rebuilt the enumeration hole. (2) `useProfiles()` puts the set of connected user ids in its query key so the map refetches when a request is sent/received/removed — otherwise a brand-new connection shows as "Unknown user" until `staleTime` lapses. (3) Any new feature that needs another user's name/avatar must go through a `viewer_access` connection (or the RPC), not a bare `select from profiles`.
- **`transactions_transfer_distinct_accounts`** check constraint: a `type = 'transfer'` row must have a `to_account`, and it can't equal `account`. The Add Entry form already prevents picking the same account on both sides client-side (`AddEntryModal.tsx`) — this is a DB-level backstop for any other write path.

## Date/time handling

**Never use `date.toISOString().slice(0, 10)` to get "today" or a local calendar date.** `toISOString()` converts to UTC first — for any user not in UTC+0 this silently returns yesterday's (or tomorrow's) date depending on time of day and offset direction. This was a real, live bug (`todayISO()` in `src/lib/format.ts`, and `toISODate()` in `src/lib/period.ts`) affecting every default transaction date, every recurring due-date/overdue check, and the dashboard's period-range boundaries for IST users.

Use `toLocalISODate(d: Date)` (in `src/lib/format.ts`) instead — builds the string from the Date object's own local `getFullYear()/getMonth()/getDate()`. `todayISO()` wraps it. If you ever see `.toISOString()` followed by `.slice(0, 10)` anywhere in this codebase, it's almost certainly a bug — the one legitimate exception is `src/lib/recurringDetection.ts`'s `addDays`/`addMonthsPreserveDay`, which construct *and* serialize entirely in UTC space (`Date.UTC(...)` → `.setUTCDate()` → `.toISOString()`), so there's no local/UTC mismatch there.

## Conventions

- **Chart/UI color semantics**: green (`text-positive` / `bg-positive-light`, or `colors.positive` in chart components) = income/credit/balance. Red = expense/debit/spend — in chart code this is still the hardcoded `colors.danger` inside `getChartTheme()` (deliberately independent of the user's accent theme, untouched), but everywhere else use the `--danger`/`--danger-light` tokens (`text-danger`, `bg-danger-light` — see Design system below) instead of hardcoding `red-600`/`red-50`. This was unified this way across the dashboard charts and the transactions credit/debit capsule — don't reintroduce the older `text-caution` (amber) styling for expenses in new UI, even though some older per-row transaction styling still uses it.
- **Credit/debit arrow direction is intentionally reversed** from the common convention: down-arrow (`ArrowDownRight`) = credit/money in, up-arrow (`ArrowUpRight`) = debit/money out. User explicitly corrected this from the more common up=in/down=out. Only `src/pages/TransactionsPage.tsx`'s header summary capsule actually uses these arrow icons — `TransactionTable.tsx`'s individual rows use colored text + a "Debit"/"Credit" word label instead, no arrow glyph (confirmed via smoke test — don't assume a per-row arrow exists when touching that table).
- **`formatCompact`** (in `useFormatCurrency()`) gives locale-aware compact currency (`$1.2K`, `₹4.6L`) for glanceable summaries — prefer it over hand-rolled `Intl.NumberFormat` compact formatters.
- **Mutations always call `invalidateQueries`** on success rather than manually patching the query cache — keeps the pattern consistent across ~15 mutation hooks in `src/hooks/`.
- **No realtime subscriptions, and no background jobs except the daily reminder job** (see "Phone reminders" below -- the only scheduled thing; it sends notes, it never changes data like `next_date`). Nothing ever advances a recurring item's `next_date` on its own, and nothing pushes cross-user updates into an open tab. Two consequences to remember:
  - Notification-relevant queries that depend on *another user's* action (admin feedback inbox, reply notices, incoming access requests) need `refetchInterval` polling to update without a manual reload — plain `refetchOnWindowFocus` only helps for the same user's own actions across their own tab switches.
  - "Mark as paid" on a recurring/subscription item is the only thing that ever moves its `next_date` forward, and it now also logs a real expense transaction (see `useRecurring.ts`'s `markPaid` mutation) — previously it silently only moved the date. It steps from the current `next_date` (not the payment date) and keeps `recurring_items.anchor_day`, so a 31st bill goes Jan 31 → Feb 28 → Mar 31; a manual edit of `next_date` resets the anchor (trigger `recurring_items_keep_anchor_day`).
- **Offline = read-only cached data, nothing more.** `QueryPersistence` (`src/components/layout/QueryPersistence.tsx`, mounted inside `AuthProvider`) saves the signed-in user's TanStack query cache to IndexedDB (`src/lib/idbStore.ts`, no dependency — structured clone, so `Map`s survive) on a 2s throttle and `hydrate()`s it on the next load; `OfflineBanner` shows when `navigator.onLine` is false. Rules (`src/lib/queryPersistence.ts`, unit-tested): restored only for the **same userId** and only if saved within 7 days; both the in-memory cache and the saved blob are **wiped on sign-out** (userId → null transition); filtered Transactions-list variants aren't saved (unbounded). A saved cache also carries `PERSISTED_CACHE_VERSION` and is only restored at the same version -- bump it whenever a release changes the shape of cached data (1.7.0 renamed account kind `bank` → `savings`, and a pre-1.7 cache crashed Home before the refetch landed). `useAccountDetails` also runs `normalizeAccountKind` in a `select` (which runs on restored data too), and `AccountKindIcon` falls back to the bank icon. `gcTime` is raised to 24h app-wide so pages visited earlier in the session are still there to save. There is no offline write queue: a mutation made offline is paused by TanStack and only completes if the tab is still open when the connection returns — don't claim more than that in UI copy. Known trade-off: an un-signed-out user's financial data stays in that browser's IndexedDB for up to 7 days (same exposure class as the Supabase session already in localStorage).
- **iOS home-screen (standalone) layout: size header rows *below* `--safe-top`, never including it.** `TopBar`'s header is `pt-[var(--safe-top)]` with `min-h-[calc(76px+var(--safe-top))]`, so the 76px button row always sits under the status bar / Dynamic Island. It used to be `min-h-[76px]`: with border-box sizing the ~69px safe-area padding ate that 76px, the row collapsed onto the bottom border, and the fixed logo toggle (`Sidebar`, `top-[calc(1rem+var(--safe-top))]` — positioned for a full 76px row) ended up lower than the buttons and overlapping the border. Invisible in a browser tab (safe area = 0); only shows on an installed PWA. Anything else pinned relative to the header (the mobile notifications panel, `top-[calc(76px+var(--safe-top))]`) must add `--safe-top` too. To test without an iPhone: set `document.documentElement.style.setProperty('--safe-top', '69px')` on a 375px-wide viewport and check the logo and the header buttons share a vertical center.
- **Don't use plain `text-accent` for text or icons.** `--accent` isn't overridden for dark mode (it's also the fill behind white button text, so it can't just be brightened), and deep presets like Oxblood render it near-invisible on dark surfaces — this made the active bottom-nav tab unreadable (~1.3:1). Use `text-accent-dark` for standalone text/icons/links (brightened in dark mode; 5.97:1 for the active tab) and `text-accent-on-light` on `bg-accent-light`. `bg-accent`, `border-accent` and `ring-accent` are fine. There are currently no plain `text-accent`/`hover:text-accent` uses left — keep it that way.
- **PWA update handling**: `src/components/layout/UpdateBanner.tsx` uses `virtual:pwa-register/react` to poll for a new service worker periodically and show a "new version available" prompt. `vite.config.ts` uses `registerType: 'prompt'` — with `'autoUpdate'` the plugin never calls `onNeedRefresh` and instead reloads every open tab by itself when the new worker activates, discarding half-typed input.
- **Loan / EMI details on recurring payments** (migration `2026-09-29_recurring_loan_details.sql`): `recurring_items.loan_amount`, `loan_tenure_months` (1-600) and `loan_start_date` (1st of the first EMI's month) -- all three or none -- plus an optional `loan_interest_rate` (% a year, 0-100, only alongside the others; `recurring_items_loan_interest_rate_check`). With amount, rate and tenure filled in, the form offers the standard reducing-balance EMI (`emiFor`) as a one-tap "Use this amount" (`recurring_items_loan_details_check`, explicit IS NOT NULLs). Set in the recurring form's "This is a loan / EMI" section (recurring kind only; monthly-or-longer cadence). **EMIs paid is derived, not stored**: `loanProgress` (`src/lib/loans.ts`, unit-tested) counts every installment due before the item's `next_date` as paid -- "Mark paid" is the only thing that advances it, and it also covers EMIs paid before the user started tracking, which counting logged transactions would miss. `ConfirmedItemRow` shows "N of M EMIs paid", a bar, remaining + end month, repaid/total payable and the implied interest (total EMIs − loan amount).
- **Recurring rows are plain list rows** (`ConfirmedItemRow`): category icon, name + amount, cadence · account, next/overdue date, loan progress; tap the row to edit (the edit sheet's header deletes), a switch pauses it, and a "Paid" pill appears only when overdue. No tinted cards. Low balance is judged **per account** by `accountShortfalls` (`src/lib/recurringShortfall.ts`, tested: sum of active items' next payments vs the balance, credit cards excluded) and explained **once per account** in an amber note above the list ("X has ₹A, and the next N payments need ₹B · Update its balance"); rows only mark the account name amber. It used to repeat a red "Low balance" sentence under every row.
- **Recurring/subscription items require an `account`** (added this session — previously optional). A row created before that change can still have `account: null`; UI in `ConfirmedItemRow.tsx` and `OverdueRecurringAlerts.tsx` must handle that gracefully (route to Edit / show "Add account" rather than silently rendering nothing where a "mark as paid" button should be).
- **Custom accounts** are added in Settings (categories can also be added inline with QuickAddCategory -- see above); **custom categories/tags** were added in Settings — categories/tags via `ManagedListEditor`, accounts and cards via Accounts & cards (`AccountsManager`) — not inline from any add-transaction/add-recurring form — there is no inline "+ add new category" affordance anywhere in this app; don't build a picker that filters out anything not in a hardcoded default list without also explicitly re-including anything the user added themselves (this was a real bug: the recurring/subscription category picker's curated relevant-categories filter initially hid custom categories entirely).
- **The duplicate-transaction guard (`buildFingerprint` in `src/lib/fingerprint.ts`, unique on `(owner_user_id, fingerprint)`) is date+merchant+amount+account, plus a `|income` or `|transfer|<to account>` suffix for those types (expense fingerprints have no suffix, so `mark_recurring_item_paid`'s SQL copy stays identical) — it doesn't know about category.** Editing a transaction keeps its stored fingerprint unless date/amount/type/account/to-account changed, so tidying an imported row's merchant doesn't make a re-import duplicate it. Two genuinely different transactions (e.g. two same-day, same-amount purchases at the same merchant/account, logged under different categories) collide and get rejected as a false-positive duplicate. `AddEntryModal.tsx` catches this as a typed `DuplicateTransactionError` (thrown by `useAddTransaction`/`useUpdateTransaction` in `useTransactions.ts`) and offers a "Save anyway" button, which retries with `allowDuplicate: true` — that appends a random suffix to the fingerprint (`withDuplicateOverride`) so it can't collide again, without changing `buildFingerprint`'s own canonical output (CSV import's upsert/`ignoreDuplicates` dedup still matches against the un-suffixed fingerprint).

- **Motion system already exists** in `src/index.css` — `.animate-fade-in`, `.animate-scale-in`, `.animate-fade-in-up`, `.animate-pop-in`, `.animate-shadow-breathe`, `.animate-shake`, `.animate-toast-in`/`-out`, `.skeleton` shimmer (with a `prefers-reduced-motion` fallback), `.card-interactive` (hover lift + shadow + border, active press) — all on `cubic-bezier(0.16, 1, 0.3, 1)`. Reuse these classes; don't add a parallel animation system.
- **Every dark-mode `.dark[data-accent='X']` block needs an `--accent-dark` override, not just `--accent-light`.** `--accent-light` is a tinted background (pills, badges, active-nav, banners — `Pill.tsx`, `Avatar.tsx`, `Sidebar.tsx`, `RecurringLikePage.tsx`'s banner), `--accent-dark` is the text/icon color drawn on top of it. Each preset darkens `--accent-light` for dark mode, but until this was fixed no preset gave `--accent-dark` a matching dark-mode value — it stayed pinned to its light-mode shade (tuned for a near-white background), which converges to nearly the same color as the new dark `--accent-light` and makes the pairing unreadable. `charcoal` had it worst (no hue to fall back on at all — its dark-mode `--accent-light` is now kept *light*, like light mode, instead of darkened) but every preset had some version of this; each now gets a brightened `--accent-dark` for dark mode alongside its `--accent-light` override.
- **`--accent-dark` has two different jobs that only `charcoal` needs split apart: standalone (wordmark, plain hover-text links — needs to be *bright* in dark mode, since it sits on a dark page/card) vs. drawn on top of `--accent-light` (pills, badges, `SummaryCard`'s highlighted Net Worth card — needs to *contrast* with whatever `--accent-light` actually is).** For 9 of the 10 presets these coincide because dark mode darkens `--accent-light` too, so one bright `--accent-dark` value works for both. `charcoal` is the outlier (its `--accent-light` deliberately stays light in dark mode, see above), so a brightened `--accent-dark` there reads as near-white-on-near-white when paired with `--accent-light` — confirmed via smoke test as a real WCAG failure (~1.3:1) on the Net Worth card. Fixed with a second token, **`--accent-on-light`** (`text-accent-on-light` in Tailwind): defaults to `var(--accent-dark)` everywhere (zero visual change for 9 presets) and is only overridden — back to the light-mode-dark value — in `.dark[data-accent='charcoal']`. **Any new "text drawn on top of `bg-accent-light`" UI must use `text-accent-on-light`, not `text-accent-dark`** — the ~15 existing pill/badge/tinted-card call sites were all migrated; grep for `bg-accent-light` before adding a new one to see the pattern. One more spot needed a *separate* fix beyond this token: `SummaryCard`'s value span (the actual number) uses plain `text-slate-900`, which a blanket `.dark .text-slate-900 { color: #f8fafc }` rule (index.css) flips to near-white — correct when the highlighted card's background is dark, wrong for charcoal's light one. Fixed with a narrowly-scoped override, `.dark[data-accent='charcoal'] .bg-accent-light .text-slate-900`, rather than making the value span itself accent-aware (which would've also recolored the number for the other 9 already-approved presets).
- **`Card` (`src/components/ui/Card.tsx`) omits its own `bg-app-card`/`border-app-border` defaults when the caller's `className` supplies a `bg-`/border-color override** (e.g. `bg-accent-light`, `bg-red-50/40`). Tailwind emits same-property utilities in a fixed internal order (alphabetical-ish by class name, not by `tailwind.config.ts` key order or by position in `className`), so `bg-app-card` was winning over a caller's `bg-accent-light` in the generated stylesheet regardless of source order — Card's own background silently beat every attempt to tint it. Any future "same CSS property, two classes on one element" pattern needs the same treatment (omit-the-default, not reorder-the-config — reordering `tailwind.config.ts`'s color keys does not change generation order).

## Versioning

`package.json`'s `version` and `src/lib/whatsNew.ts`'s `APP_VERSION` are kept in sync by hand (no automated bump). `WHATS_NEW_ITEMS` is a flat list of the *current* release's highlights (replaced wholesale each release, not accumulated) — bump `CURRENT_WHATS_NEW_VERSION` (a date string) alongside it whenever you update the list, since that's what gates the auto-shown "What's new" modal (`WhatsNewModal.tsx`) for users who haven't seen the current version yet.
