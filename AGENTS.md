# LedgeEaze

A shared personal finance tracker (PWA). Multiple users can see each other's transactions once they approve access to each other; budgets, goals, and personal details stay private per-user.

- **Live:** https://finance-tracker.rohith24112.workers.dev
- **Stack:** React 18 + Vite + TypeScript + Tailwind + TanStack Query + React Router v6 + Recharts + lucide-react + dnd-kit
- **Backend:** Supabase (Postgres, Auth, Storage, RLS) — project id `izidxazhknyoxeqgnqdb`
- **Hosting:** Cloudflare Workers (static assets), deployed via `npm run deploy` (`wrangler` is a pinned exact-version devDependency, not fetched fresh by `npx` each time)
- **Admin:** role-based via the `admin_users` table + `is_admin()` (currently one admin, `rohith24112@gmail.com`; see RLS / access patterns below)

## Commands

```bash
npm run dev      # vite dev server, localhost:5173
npm run build    # tsc -b && vite build
npm run lint     # eslint .
npm run test     # vitest run (src/lib/*.test.ts — pure-function unit tests only, no component/integration tests yet)
npm run check    # lint && test && build, in that order
npm run deploy   # check, then wrangler deploy — deploy dist/ to Cloudflare Workers
```

Standard workflow after a batch of changes: `npm run check` (or at minimum `npx tsc -b`) → commit → push → `npm run deploy`. `.github/workflows/ci.yml` runs `npm run check` on every push/PR to `main` as a validation gate — but it only checks, it doesn't deploy; deployment is still a manual `npm run deploy` from someone's machine.

**Security regression tests:** `supabase/tests/security_regression.sql` re-asserts every access rule (no anon EXECUTE on SECURITY DEFINER functions, RLS on every public table, `admin_users` unreachable, profiles/transactions/feedback/private tables scoped correctly for QA15, admin sees all via `is_admin()`, a spoofed admin-email claim grants nothing, anon reads nothing, the transfer/FX CHECK constraints). It impersonates roles inside one transaction and **rolls back**, raising on the first failure — run the whole file via the SQL editor or `execute_sql` after any migration touching RLS, grants or functions; expect a single `ALL SECURITY CHECKS PASSED` row. It isn't in CI (CI has no database credentials).

## Database

- `supabase/schema.sql` — hand-maintained, **append-only** DDL. Represents what a fresh install would run top to bottom. When schema drifts from a migration (see Postgres gotcha below), append a correcting `alter table` block rather than editing the original `create table` in place.
- `supabase/policies.sql` — hand-maintained, the actual RLS source of truth, kept separate from schema.sql.
- Both files must be kept in sync by hand with every migration applied via `mcp__supabase__apply_migration`. There is no automatic schema dump/diff step — if you apply a migration, edit both files in the same batch.
- Every user-owned table has an `owner_user_id uuid references auth.users(id) on delete cascade` column. Deleting an account (`delete_own_account()` RPC) relies entirely on these cascades.

### Known Postgres gotcha: `on delete` clause drift

`categories`, `accounts`, and `tags` each have a `created_by` FK to `auth.users`. The live constraints were found to be missing `on delete set null` even though `schema.sql`'s `create table` statements document it — meaning any account that had ever added its own custom account/category/tag could not delete itself (the `created_by` FK blocked the cascade after every other row had already succeeded, rolling the whole delete back). Fixed via `fix_created_by_fkey_delete_action_drift`. **Lesson:** don't trust `schema.sql` as ground truth for `on delete` behavior — verify live constraint definitions with:
```sql
select conname, conrelid::regclass, pg_get_constraintdef(oid)
from pg_constraint where confrelid = 'auth.users'::regclass and contype = 'f';
```

### RLS / access patterns

- **Admin is a role, not an email.** `public.admin_users(user_id)` lists admins; `public.is_admin()` (SECURITY DEFINER, stable, authenticated-only EXECUTE) is what every admin RLS policy calls (`feedback_select_admin`, `feedback_update_admin_reply`, `profiles_select_own_or_connected`), and the client mirrors it with `useIsAdmin()` (`src/lib/admin.ts`, calls the same RPC — UI only, RLS enforces). `admin_users` has RLS on, no policies and no grants, so it isn't readable or writable through the API at all; **grant/revoke admin only from the SQL editor** (snippets in `schema.sql`) — there's deliberately no UI, which would be a privilege-escalation surface. This replaced `auth.jwt() ->> 'email' = 'rohith24112@gmail.com'` checks (and an `ADMIN_EMAIL` client constant) that had to be kept in sync by hand.
- **Narrow SECURITY DEFINER RPCs** (e.g. `mark_feedback_reply_seen`, `delete_own_account`) are used instead of a broad "user can update their own row" policy, specifically to avoid letting a user edit fields they shouldn't (e.g. their own feedback message once an admin has replied to it).
- Postgres grants `EXECUTE` to `PUBLIC` by default on function creation, **and Supabase additionally grants it to `anon` and `authenticated` explicitly** (visible in `proacl` as `anon=X`) — so `revoke execute ... from public` alone does *not* lock a function down (this was believed done for a while; the security advisor and `has_function_privilege('anon', oid, 'execute')` showed otherwise). Every SECURITY DEFINER function needs `revoke execute ... from public, anon` (and `authenticated` too for trigger/event-trigger functions, which are never RPCs — Postgres only checks EXECUTE on a trigger function at `CREATE TRIGGER` time, not when it fires). Verify a new function with `select has_function_privilege('anon', 'public.fn(args)', 'execute')`. Current state: `delete_own_account`/`mark_feedback_reply_seen`/`find_profile_by_email`/`mark_recurring_item_paid`/`set_account_opening_balance`/`is_admin` are authenticated-only; `handle_new_user`/`handle_user_email_update`/`rls_auto_enable` are callable by no one (triggers still fire — signup re-verified after the revoke).
- **Shared-viewer pattern**: `viewer_access` (status = `'approved'`) is joined against in RLS policies to let an approved viewer read another user's transactions/receipts. When adding a new user-owned resource that should be visible to approved viewers (e.g. `documents`, `storage.objects`), mirror `transactions_select_own_or_approved` — remember storage bucket policies are separate from table policies (a document row being readable doesn't mean its file bytes are).
- **`profiles` is NOT a readable user directory.** The `profiles_select_own_or_connected` policy lets you read your own row, anyone you share a `viewer_access` row with (either direction, *any* status — so incoming/outgoing/pending requests and shared-transaction owners all resolve to names), and admins (everyone, via `is_admin()`). It used to be `profiles_select_all` (any signed-in user could list every name/email/avatar). Consequences: (1) finding someone new in Settings → Sharing goes through the **`find_profile_by_email(p_email)`** SECURITY DEFINER RPC — an *exact*, case-insensitive email match only (no name search, no prefix match, can't return yourself), `revoke`d from `public`/`anon`, `grant`ed to `authenticated`; don't turn it into a prefix/name search or you've rebuilt the enumeration hole. (2) `useProfiles()` puts the set of connected user ids in its query key so the map refetches when a request is sent/received/removed — otherwise a brand-new connection shows as "Unknown user" until `staleTime` lapses. (3) Any new feature that needs another user's name/avatar must go through a `viewer_access` connection (or the RPC), not a bare `select from profiles`.
- **`transactions_transfer_distinct_accounts`** check constraint: a `type = 'transfer'` row must have a `to_account`, and it can't equal `account`. The Add Entry form already prevents picking the same account on both sides client-side (`AddEntryModal.tsx`) — this is a DB-level backstop for any other write path.

## Date/time handling

**Never use `date.toISOString().slice(0, 10)` to get "today" or a local calendar date.** `toISOString()` converts to UTC first — for any user not in UTC+0 this silently returns yesterday's (or tomorrow's) date depending on time of day and offset direction. This was a real, live bug (`todayISO()` in `src/lib/format.ts`, and `toISODate()` in `src/lib/period.ts`) affecting every default transaction date, every recurring due-date/overdue check, and the dashboard's period-range boundaries for IST users.

Use `toLocalISODate(d: Date)` (in `src/lib/format.ts`) instead — builds the string from the Date object's own local `getFullYear()/getMonth()/getDate()`. `todayISO()` wraps it. If you ever see `.toISOString()` followed by `.slice(0, 10)` anywhere in this codebase, it's almost certainly a bug — the one legitimate exception is `src/lib/recurringDetection.ts`'s `addDays`/`addMonthsPreserveDay`, which construct *and* serialize entirely in UTC space (`Date.UTC(...)` → `.setUTCDate()` → `.toISOString()`), so there's no local/UTC mismatch there.

## Conventions

- **Chart/UI color semantics**: green (`text-positive` / `bg-positive-light`, or `colors.positive` in chart components) = income/credit/balance. Red = expense/debit/spend — in chart code this is still the hardcoded `colors.danger` inside `getChartTheme()` (deliberately independent of the user's accent theme, untouched), but everywhere else use the `--danger`/`--danger-light` tokens (`text-danger`, `bg-danger-light` — see Design system below) instead of hardcoding `red-600`/`red-50`. This was unified this way across the dashboard charts and the transactions credit/debit capsule — don't reintroduce the older `text-caution` (amber) styling for expenses in new UI, even though some older per-row transaction styling still uses it.
- **Credit/debit arrow direction is intentionally reversed** from the common convention: down-arrow (`ArrowDownRight`) = credit/money in, up-arrow (`ArrowUpRight`) = debit/money out. User explicitly corrected this from the more common up=in/down=out. Only `src/pages/TransactionsPage.tsx`'s header summary capsule actually uses these arrow icons — `TransactionTable.tsx`'s individual rows use colored text + a "Debit"/"Credit" word label instead, no arrow glyph (confirmed via smoke test — don't assume a per-row arrow exists when touching that table).
- **`formatCompact`** (in `useFormatCurrency()`) gives locale-aware compact currency (`$1.2K`, `₹4.6L`) for glanceable summaries — prefer it over hand-rolled `Intl.NumberFormat` compact formatters.
- **Mutations always call `invalidateQueries`** on success rather than manually patching the query cache — keeps the pattern consistent across ~15 mutation hooks in `src/hooks/`.
- **No cron, no background jobs, no realtime subscriptions anywhere in this app.** Nothing ever advances a recurring item's `next_date` on its own, and nothing pushes cross-user updates into an open tab. Two consequences to remember:
  - Notification-relevant queries that depend on *another user's* action (admin feedback inbox, reply notices, incoming access requests) need `refetchInterval` polling to update without a manual reload — plain `refetchOnWindowFocus` only helps for the same user's own actions across their own tab switches.
  - "Mark as paid" on a recurring/subscription item is the only thing that ever moves its `next_date` forward, and it now also logs a real expense transaction (see `useRecurring.ts`'s `markPaid` mutation) — previously it silently only moved the date.
- **Offline = read-only cached data, nothing more.** `QueryPersistence` (`src/components/layout/QueryPersistence.tsx`, mounted inside `AuthProvider`) saves the signed-in user's TanStack query cache to IndexedDB (`src/lib/idbStore.ts`, no dependency — structured clone, so `Map`s survive) on a 2s throttle and `hydrate()`s it on the next load; `OfflineBanner` shows when `navigator.onLine` is false. Rules (`src/lib/queryPersistence.ts`, unit-tested): restored only for the **same userId** and only if saved within 7 days; both the in-memory cache and the saved blob are **wiped on sign-out** (userId → null transition); filtered Transactions-list variants aren't saved (unbounded). `gcTime` is raised to 24h app-wide so pages visited earlier in the session are still there to save. There is no offline write queue: a mutation made offline is paused by TanStack and only completes if the tab is still open when the connection returns — don't claim more than that in UI copy. Known trade-off: an un-signed-out user's financial data stays in that browser's IndexedDB for up to 7 days (same exposure class as the Supabase session already in localStorage).
- **iOS home-screen (standalone) layout: size header rows *below* `--safe-top`, never including it.** `TopBar`'s header is `pt-[var(--safe-top)]` with `min-h-[calc(76px+var(--safe-top))]`, so the 76px button row always sits under the status bar / Dynamic Island. It used to be `min-h-[76px]`: with border-box sizing the ~69px safe-area padding ate that 76px, the row collapsed onto the bottom border, and the fixed logo toggle (`Sidebar`, `top-[calc(1rem+var(--safe-top))]` — positioned for a full 76px row) ended up lower than the buttons and overlapping the border. Invisible in a browser tab (safe area = 0); only shows on an installed PWA. Anything else pinned relative to the header (the mobile notifications panel, `top-[calc(76px+var(--safe-top))]`) must add `--safe-top` too. To test without an iPhone: set `document.documentElement.style.setProperty('--safe-top', '69px')` on a 375px-wide viewport and check the logo and the header buttons share a vertical center.
- **Don't use plain `text-accent` for text or icons.** `--accent` isn't overridden for dark mode (it's also the fill behind white button text, so it can't just be brightened), and deep presets like Oxblood render it near-invisible on dark surfaces — this made the active bottom-nav tab unreadable (~1.3:1). Use `text-accent-dark` for standalone text/icons/links (brightened in dark mode; 5.97:1 for the active tab) and `text-accent-on-light` on `bg-accent-light`. `bg-accent`, `border-accent` and `ring-accent` are fine. There are currently no plain `text-accent`/`hover:text-accent` uses left — keep it that way.
- **PWA update handling**: `src/components/layout/UpdateBanner.tsx` uses `virtual:pwa-register/react` to poll for a new service worker periodically and show a "new version available" prompt — `registerType: 'autoUpdate'` alone in `vite.config.ts` does not proactively push a new build into an already-open tab (a real problem for a PWA people keep pinned open for days).
- **Recurring/subscription items require an `account`** (added this session — previously optional). A row created before that change can still have `account: null`; UI in `ConfirmedItemRow.tsx` and `OverdueRecurringAlerts.tsx` must handle that gracefully (route to Edit / show "Add account" rather than silently rendering nothing where a "mark as paid" button should be).
- **Custom categories/accounts/tags** are added via Settings → Financial setup (`ManagedListEditor`), not inline from any add-transaction/add-recurring form — there is no inline "+ add new category" affordance anywhere in this app; don't build a picker that filters out anything not in a hardcoded default list without also explicitly re-including anything the user added themselves (this was a real bug: the recurring/subscription category picker's curated relevant-categories filter initially hid custom categories entirely).
- **The duplicate-transaction guard (`buildFingerprint` in `src/lib/fingerprint.ts`, unique on `(owner_user_id, fingerprint)`) is date+merchant+amount+account only — it doesn't know about category.** Two genuinely different transactions (e.g. two same-day, same-amount purchases at the same merchant/account, logged under different categories) collide and get rejected as a false-positive duplicate. `AddEntryModal.tsx` catches this as a typed `DuplicateTransactionError` (thrown by `useAddTransaction`/`useUpdateTransaction` in `useTransactions.ts`) and offers a "Save anyway" button, which retries with `allowDuplicate: true` — that appends a random suffix to the fingerprint (`withDuplicateOverride`) so it can't collide again, without changing `buildFingerprint`'s own canonical output (CSV import's upsert/`ignoreDuplicates` dedup still matches against the un-suffixed fingerprint).
- **CSV export** (`src/lib/csvExport.ts`, via `papaparse`'s `Papa.unparse`, wired into `TransactionsPage.tsx`'s "Export" button) exports the same scope+period-filtered set the header credit/debit totals are computed from (`inPeriod`) — not the table's own search/type/category/account/person filters below, which narrow what's *browsed*, not what's exported. Date is kept as raw ISO (`YYYY-MM-DD`), not locale-formatted, so the file re-imports cleanly through this app's own CSV import. The "Everyone" scope adds an `Owner` column (resolved via `profiles.data`); "Mine" doesn't. **Every user-controlled string field (merchant, category, account, remarks, tags, owner display name) goes through `sanitizeCsvField()` first** — a value starting with `=`, `+`, `-`, `@`, tab, or CR gets a leading `'` prepended, since Excel/Sheets/LibreOffice otherwise interpret it as a formula when the file is opened (up to a DDE/shell-command payload via `=cmd|'/c ...'!A1`-style values) — and this is attacker-reachable since a shared viewer can trigger an export containing another user's transaction text. Any new export/report feature that writes user-controlled text into a CSV needs the same treatment.
- **`TransactionsPage`'s browsable list and its header credit/debit capsule intentionally read from two separate queries.** `useMyTransactionsPaginated`/`useEveryoneTransactionsPaginated` (`useTransactions.ts`, `useInfiniteQuery`, `TRANSACTIONS_PAGE_SIZE = 100` rows via `.range()`) feed the table with a "Load more" footer (in `TransactionTable.tsx`, also surfaced inside `EmptyState` when a search/filter matches nothing *loaded* but more pages exist) — this isn't capped at `TRANSACTIONS_QUERY_LIMIT`. The header capsule still reads from the original flat `useMyTransactions`/`useEveryoneTransactions` (capped, unchanged), because it needs a correct period-wide sum, not just whatever's been paged into view. **Don't collapse these into one query** — the aggregate-math consumers (this capsule, plus budgets/dashboard/account-balances elsewhere, which weren't touched by this change) need the full set; the browsable list needs incremental loading. **Search, the type/category/account/person dropdowns, and the selected period are applied server-side** (`fetchTransactionsPage` in `useTransactions.ts`; filter state lives in `TransactionsPage`, is debounced 300ms via `useDebouncedValue`, and is passed into `TransactionTable` as controlled props), so they reach the whole history, not just what's been paged in; `placeholderData: keepPreviousData` keeps the old rows on screen while a new search loads. The pure escaping/`or()`-string logic is in `src/lib/transactionSearch.ts` (unit-tested) — any user text going into a PostgREST `.or()` must go through `quotePostgrestValue`/`escapeLike`, or a comma or parenthesis in the input breaks out of the filter list. **Behavior difference from the old client-side search: tag matching is now an exact, case-sensitive element match** (PostgREST can't substring-match inside a `text[]`); merchant and category stay case-insensitive substring. Person-filter options come from the unfiltered full-fetch data so they don't shrink as you filter.
- **Bulk select/edit/delete** lives in `TransactionTable.tsx` (local `selected: Set<string>` state, a checkbox column in both the desktop grid and mobile card layouts, a "N selected" bar with a bulk category `Dropdown` + Delete, and a lightweight Cancel/Delete confirm `Modal` — no type-to-confirm, matching the fact single-row delete has no confirmation either). Only rows the signed-in user owns get a checkbox. `useBulkDeleteTransactions`/`useBulkUpdateTransactionCategory` (`useTransactions.ts`) each issue one `.in('id', ids)` request; ownership is enforced per-row by the existing `transactions_delete_own`/`transactions_update_own` RLS, not client-side. Both the mobile and desktop layouts always render in the DOM (one hidden via CSS), so every row has *two* checkboxes — query with `offsetParent !== null` when scripting the visible one. The grid column templates gained a leading `28px` checkbox column; keep header and row templates in sync if you touch either.
- **Duplicate review** (`Duplicates` button on `TransactionsPage` → `DuplicatesModal.tsx`, logic in `src/lib/duplicates.ts`, unit-tested): `findDuplicateGroups()` clusters the *signed-in user's own* transactions (always `useMyTransactions`, regardless of the Mine/Everyone toggle — you can only delete your own) that share type + account(s) + amount, fall within `DUPLICATE_WINDOW_DAYS` (3) of each other, and have a similar merchant (`merchantsSimilar` from `src/lib/merchant.ts` — equal after normalization, or one contains the other with ≥4 chars). It is deliberately the *tolerant* counterpart to the strict unique fingerprint: it exists for near-misses (manual entry + CSV import of the same purchase with a different merchant string/posting date, or rows created via "Save anyway"). It only suggests — "Keep this one" bulk-deletes the rest of the group, "Not a duplicate" hides the group for that open only (dismissals aren't persisted; that would need a table). **QA note:** the standing regression fixtures ("RPC Test Item", "QA Atomic Verify Item") are a legitimate same-amount/adjacent-day pair each, so they'll always show up here — don't "Keep this one" on them.
- **`TRANSACTIONS_QUERY_LIMIT`** (`src/hooks/useTransactions.ts`, currently 5,000) is the hard cap on both `useMyTransactions`/`useEveryoneTransactions` — there's no pagination. `TransactionsPage` shows a caution banner when the fetched list length exactly equals the cap (the one observable signal a plain `.limit()` gives you that older rows got silently cut off).
- **Multi-currency = convert at entry time, store both.** `transactions.amount` is *always* in the owner's home currency (`user_settings.currency`), so every existing sum, budget, balance, chart and the duplicate fingerprint work unchanged. A foreign-currency expense/income (Add Entry's Currency picker; transfers stay home-currency) also stores `original_currency` / `original_amount` / `fx_rate`, with `amount = round(original_amount × fx_rate, 2)` (`convertToHome` in `src/lib/fx.ts`, unit-tested). The rate is fetched from Frankfurter (`api.frankfurter.dev/v1`, ECB reference rates, keyless — only the two codes and the date leave the browser; weekends fall back to the last business day), pre-filled and editable; if the lookup fails the user types the rate. It is **fixed at entry** — nothing re-converts later (no cron). Editing a foreign entry keeps its stored rate unless the currency or date changes. The list shows "€20.00 · Debit" under the home amount; CSV export adds Original amount/currency/Exchange rate columns. `transactions_original_currency_check` requires all three fields or none. **Limits to remember:** changing your home currency in Settings does *not* re-express existing amounts (pre-existing behavior); a shared viewer sees the owner's home-currency `amount` formatted in the *viewer's* currency (also pre-existing — profiles don't expose the owner's currency); CSV *import* still assumes home currency.
- **CHECK constraints and NULL:** a CHECK passes when its expression is NULL, so `a OR (b AND c)` with a NULL operand can silently accept bad rows — write explicit `IS NOT NULL`s (this bit `transactions_original_currency_check`'s first version). `transactions_transfer_distinct_accounts` originally had the same shape and let a transfer with a NULL `to_account` through; it now also requires `to_account is not null`.
- **Opening (starting) balances** live on `accounts.opening_balance` and are set only through the **`set_account_opening_balance(p_account, p_amount)`** SECURITY DEFINER RPC (own accounts only, authenticated-only) — `accounts` intentionally has no UPDATE policy, since a broad one would allow renames that orphan transactions' `account` references. `calculateAccountBalances(transactions, openingBalances)` seeds from them, and every balance consumer goes through `useAccountBalances` (dashboard balances/bar chart, transfer overdraw hint, recurring "insufficient balance"), so there's one place to change. Edited in Settings → Financial setup → Starting balances (`StartingBalances.tsx`; negative allowed for credit cards). This is separate from, and coexists with, the manual Net worth totals (`user_settings.assets_total`/`liabilities_total`) — those aren't derived from accounts.
- **Budget rollover is opt-in per budget (`budgets.rollover`, default false).** `BudgetCard` always shows "Last month: ₹X left over / ₹X over" (`priorMonthResult`, measured against the *base* limit). With rollover on, `effectiveLimit()` (`src/lib/budgets.ts`, unit-tested) adds only a *positive* leftover to this month's limit -- overspending never shrinks next month. `applyRollover()` in `useBudgets.ts` returns `EffectiveBudget`s (`monthly_limit` = effective, plus `baseLimit`/`carried`) and is used by `BudgetsPage`, `useBudgetAlerts` and the Monthly review, so alerts and "over budget" follow the effective limit. Caveats: it's one month deep (last month's own carry isn't compounded) and last month is judged at today's limit, since limit edit history isn't stored. Editing a budget must pass `baseLimit` into the form, never the effective limit (`BudgetsPage` does this).
- **Bills (`/bills`, `BillsPage.tsx`) and Monthly review (`/review`, `ReviewPage.tsx`)** are in the phone bottom nav (Home, Activity, a centre Add button, Review, Bills -- `BOTTOM_NAV_ITEMS` in `navItems.ts` + `BottomNav.tsx`; the top-bar Add button is md+ only; Budgets/Recurring/Subscriptions/Goals/Documents/Rules/Shared are sidebar-only). Bills projects every active recurring item/subscription forward from its `next_date` by cadence (`dueDatesInRange`/`totalDueWithin`/`monthGrid` in `src/lib/billCalendar.ts`, unit-tested, UTC-space date math) -- a read-only projection; "Mark paid" (the existing RPC) is still the only thing that moves `next_date`, and it's only offered on an item's actual due/overdue `next_date`. Review uses `buildMonthlyReview` (`src/lib/monthlyReview.ts`, unit-tested; own transactions only, transfers excluded).
- **Home-screen shortcuts**: `manifest.shortcuts` in `vite.config.ts` (Add entry → `/?add=entry`, Bills, Monthly review). `GlobalModalsProvider` opens Add entry when it sees `?add=entry` and strips the param with `history.replaceState`.
- **`Modal` is a bottom sheet below `sm`** (slides up via `.animate-sheet-up`, grab handle, bottom safe-area padding) and the centered card from `sm` up. Add entry's category picker is a chip group over the full `categoryOptions` list (custom categories included). Phone-width transaction lists show day headings ("Today · …") between rows; the desktop table keeps its Date column.
- **Split and settle up** (`transaction_splits`, `/shared` → `SharedPage.tsx`, `SplitModal.tsx` opened via `useGlobalModals().openSplit` from the Split button on your own expense rows in `TransactionTable`). The payer (`owner_user_id`) records what a connected person (`with_user_id`) owes; `description`/`date` are copied from the transaction so the other person has context without being able to read the payer's transactions. RLS: both participants can SELECT; only the payer can INSERT/UPDATE/DELETE, only on their own *expense*, for no more than its amount, and only with someone they have an **approved** `viewer_access` row with (either direction) -- the same connection check is on UPDATE's WITH CHECK so a split can't be re-pointed at a stranger. anon has no grant at all. Only the payer can mark settled (they know the money arrived). Balances: `splitBalances` in `src/lib/splits.ts` (unit-tested). `useSplits` polls every 30s (the other person acts from their own session; no realtime).
- **Smart categories** (`suggestCategory` in `src/lib/smartCategory.ts`, unit-tested): Add entry offers "Use X, like last time" from the user's own past entries of the same type at a similar merchant (`merchantsSimilar`), most-used category wins, ties go to the most recent. A suggestion only -- never auto-applied, never shown when editing.
- **Saved filters** on Transactions (`SavedFilters.tsx`, pure logic in `src/lib/savedFilters.ts`, unit-tested): up to 8 filter sets, stored per user in **localStorage only** (`ledgeeaze:saved-filters:<userId>`, every access in try/catch) -- a per-browser convenience, not synced.
- **Balance over time** on Monthly review: `monthEndBalances` (`src/lib/balanceHistory.ts`, unit-tested) derives month-end totals from starting balances + income − expenses (transfers net to zero) -- no stored snapshots.
- **Motion utilities** added to `index.css` alongside the existing ones: `.stagger-rows` (children rise 60ms apart, capped at 8), `.animate-bar-grow` (ProgressBar fills from zero), `.animate-bar-rise` (vertical bars), `.animate-sheet-up` (Modal on phones); all have `prefers-reduced-motion` fallbacks.
- **Add entry's category picker is one horizontally scrolling chip row** spanning the full form width (it used to wrap into a tall block beside Account); the selected chip is scrolled into view horizontally with `row.scrollTo`, not `scrollIntoView` (which would also scroll the sheet).
- **Never run `npx prettier --write` on a file here** -- the repo has no Prettier config, so it rewrites the whole file in a different style (double quotes, semicolons). It happened once to `TransactionTable.tsx` and had to be reverted by hand.
- **Credit cards vs debit cards.** `accounts.kind` is `bank | credit_card | cash | wallet` (default `bank`; the migration backfilled `Cash` -> cash and names ending " Card" / containing "credit card" -> credit_card). **A debit card is not an account** -- it's `payment_method = 'Debit card'` on the bank account. A credit card is an account whose balance uses the same sign as every other account (spends make it negative = owed); card spends are expenses on the purchase date and **paying the bill is a transfer bank -> card, never an expense** (no double counting). Card-only fields `credit_limit`, `statement_day`, `due_day` must be null for other kinds (`accounts_card_fields_only_on_cards`). Like the opening balance, they're set only through the narrow **`set_account_details(p_account, p_kind, p_credit_limit, p_statement_day, p_due_day)`** SECURITY DEFINER RPC (own accounts only, authenticated-only; it nulls card fields for non-card kinds) -- `accounts` still has no UPDATE policy. UI: Settings -> Financial setup -> "Account types and cards" (`AccountTypes.tsx`). **Closed accounts**: `accounts.closed_at` set via the narrow `set_account_closed(p_account, p_closed)` RPC; closed accounts keep their transactions but are hidden from account chips (unless already selected), dashboard balances/totals and card bills (`useClosedAccounts` in `useCards.ts`). Logic in `src/lib/creditCards.ts` (unit-tested): `cardStatus` -> owed / credit (overpaid) / available / utilization and, when both days are set, the **bill = owed at the end of the last statement date minus payments into the card since** (later spends go on the next bill), due on the first `due_day` after the statement date; days past a month's end clamp (31 -> 30 Sep). `cashAndCardDebt` splits per-account balances into cash vs card debt (Home hero shows net plus "X in accounts · Y owed on cards"). Hooks in `src/hooks/useCards.ts` (`useAccountKinds`, `useCardStatuses`, `useCardBills`). Consequences wired in: card accounts never get "insufficient balance"/overdraft hints (`RecurringLikePage`, `OverdueRecurringAlerts`, Add entry, Bills shortfalls); Account balances lists cards separately (owed, available, utilization bar, bill due); unpaid card bills appear on the Bills calendar, in Coming up (with "Pay bill", which opens Add entry as a transfer pre-filled with the card and amount via `openAddEntry(type, prefill)`) and in Home's "Due this week"; choosing a card account in Add entry fills the payment method with "Credit card"; account chips show a card icon.

- **Merchant matching** (`src/lib/merchant.ts`, unit-tested) is the one shared *tolerant* notion of "same merchant": `normalizeMerchant` (lowercase, strip punctuation, trailing `#1234`, 6+-digit reference numbers), `merchantsSimilar` (duplicate review) and `merchantContains` (Rules — a rule's "when" text matches either as plain case-insensitive substring *or* after normalizing both sides, so "uber trip" matches "UBER *TRIP 88123456"; a needle that normalizes to nothing, like "#12", only gets the plain check so it can't match every merchant). Recurring detection re-exports `normalizeMerchant` from here. **Intentionally not used by `buildFingerprint`** (strict trim+lowercase, since it's a hard unique constraint) and never used to rewrite stored merchant text.
- **CSV import amount/date parsing** (`src/lib/csvImport.ts`): `parseAmount()` strips any currency symbol (not just `$`), treats a parenthesized amount as negative (`"(45.00)"` — a common bank-export debit convention), and disambiguates US (`1,234.56`) vs European (`1.234,56`) thousands/decimal separators by treating whichever of `.`/`,` appears *last* in the string as the decimal point. `normalizeDate()` only swaps day/month for slash- or dot-separated dates when the swap is unambiguous (one of the two numbers is `>12` and so can't be a month, e.g. `25/12/2026`) — when both numbers are `<=12` (e.g. `03/04/2026`) it's genuinely ambiguous from the string alone and keeps assuming MM/DD/YYYY, same as before. Don't try to "fix" the ambiguous case with a smarter default; there isn't one without a per-import locale hint.

## Design system & theming

- **Accent theme presets** live in three places that must be kept in sync by hand: `ACCENT_HEX` in `src/lib/themeColors.ts`, the `ThemeAccent` union in `src/types/database.types.ts`, and the `ACCENTS` array in `src/components/settings/ThemeSettings.tsx` (plus a separate `'custom'` hex-picker path that isn't a preset). Presets: `oxblood` (current default, listed first), `violet` (original default), `ocean`, `sunset`, `pink`, `green`, `sage`, `mauve`, `plum`, `crimson`, `charcoal`. This is a genuine per-user product feature — never hardcode one color over it.
- **`oxblood` (`#5C1B2E`) is the current default**: new signups get it (`supabase/schema.sql`'s `theme_accent` column default + check constraint), and it's the pre-auth/unauthenticated fallback (`index.html`'s inline pre-mount script and `theme-color` meta, `vite.config.ts`'s PWA `manifest.theme_color`). It does **not** retroactively override any existing user's already-saved `theme_accent` — check `ThemeContext.tsx`'s fallback values if you touch this.
- **`--danger` / `--danger-light`** CSS custom properties (`src/index.css`, wired into `tailwind.config.ts` the same way as `positive`/`caution`/`info`) close a gap where every error/destructive tone used to hardcode `red-600`/`red-50`. Prefer `text-danger`/`bg-danger-light` in new UI.
- **`PageHeader`** (`src/components/ui/PageHeader.tsx`) is the shared `{ title, actions? }` page-header component (serif `text-2xl font-semibold` title) — used by Dashboard, Transactions, Budgets, Goals, Rules, Documents, Settings, and `RecurringLikePage` (shared by Recurring + Subscriptions). Use it for any new top-level page instead of hand-rolling the `<h1>` + actions-row markup. (Settings had its own hand-rolled sans-serif `text-xl` `<h1>` until a smoke test flagged the divergence — migrated to `PageHeader` with no `actions`.)
- **`AuthLayout`'s `split` prop** (`src/components/auth/AuthLayout.tsx`) renders the split-screen layout — an accent-tinted brand panel with `BrandHeader` + headline/supporting text on the left (`hidden lg:flex`), collapsing to a single centered `<Card>` below `lg` — used by all four auth pages (Login/Signup/Forgot/Reset).
- **Motion system already exists** in `src/index.css` — `.animate-fade-in`, `.animate-scale-in`, `.animate-fade-in-up`, `.animate-pop-in`, `.animate-shadow-breathe`, `.animate-shake`, `.animate-toast-in`/`-out`, `.skeleton` shimmer (with a `prefers-reduced-motion` fallback), `.card-interactive` (hover lift + shadow + border, active press) — all on `cubic-bezier(0.16, 1, 0.3, 1)`. Reuse these classes; don't add a parallel animation system.
- **Every dark-mode `.dark[data-accent='X']` block needs an `--accent-dark` override, not just `--accent-light`.** `--accent-light` is a tinted background (pills, badges, active-nav, banners — `Pill.tsx`, `Avatar.tsx`, `Sidebar.tsx`, `RecurringLikePage.tsx`'s banner), `--accent-dark` is the text/icon color drawn on top of it. Each preset darkens `--accent-light` for dark mode, but until this was fixed no preset gave `--accent-dark` a matching dark-mode value — it stayed pinned to its light-mode shade (tuned for a near-white background), which converges to nearly the same color as the new dark `--accent-light` and makes the pairing unreadable. `charcoal` had it worst (no hue to fall back on at all — its dark-mode `--accent-light` is now kept *light*, like light mode, instead of darkened) but every preset had some version of this; each now gets a brightened `--accent-dark` for dark mode alongside its `--accent-light` override.
- **`--accent-dark` has two different jobs that only `charcoal` needs split apart: standalone (wordmark, plain hover-text links — needs to be *bright* in dark mode, since it sits on a dark page/card) vs. drawn on top of `--accent-light` (pills, badges, `SummaryCard`'s highlighted Net Worth card — needs to *contrast* with whatever `--accent-light` actually is).** For 9 of the 10 presets these coincide because dark mode darkens `--accent-light` too, so one bright `--accent-dark` value works for both. `charcoal` is the outlier (its `--accent-light` deliberately stays light in dark mode, see above), so a brightened `--accent-dark` there reads as near-white-on-near-white when paired with `--accent-light` — confirmed via smoke test as a real WCAG failure (~1.3:1) on the Net Worth card. Fixed with a second token, **`--accent-on-light`** (`text-accent-on-light` in Tailwind): defaults to `var(--accent-dark)` everywhere (zero visual change for 9 presets) and is only overridden — back to the light-mode-dark value — in `.dark[data-accent='charcoal']`. **Any new "text drawn on top of `bg-accent-light`" UI must use `text-accent-on-light`, not `text-accent-dark`** — the ~15 existing pill/badge/tinted-card call sites were all migrated; grep for `bg-accent-light` before adding a new one to see the pattern. One more spot needed a *separate* fix beyond this token: `SummaryCard`'s value span (the actual number) uses plain `text-slate-900`, which a blanket `.dark .text-slate-900 { color: #f8fafc }` rule (index.css) flips to near-white — correct when the highlighted card's background is dark, wrong for charcoal's light one. Fixed with a narrowly-scoped override, `.dark[data-accent='charcoal'] .bg-accent-light .text-slate-900`, rather than making the value span itself accent-aware (which would've also recolored the number for the other 9 already-approved presets).
- **`Card` (`src/components/ui/Card.tsx`) omits its own `bg-app-card`/`border-app-border` defaults when the caller's `className` supplies a `bg-`/border-color override** (e.g. `bg-accent-light`, `bg-red-50/40`). Tailwind emits same-property utilities in a fixed internal order (alphabetical-ish by class name, not by `tailwind.config.ts` key order or by position in `className`), so `bg-app-card` was winning over a caller's `bg-accent-light` in the generated stylesheet regardless of source order — Card's own background silently beat every attempt to tint it. Any future "same CSS property, two classes on one element" pattern needs the same treatment (omit-the-default, not reorder-the-config — reordering `tailwind.config.ts`'s color keys does not change generation order).

## Versioning

`package.json`'s `version` and `src/lib/whatsNew.ts`'s `APP_VERSION` are kept in sync by hand (no automated bump). `WHATS_NEW_ITEMS` is a flat list of the *current* release's highlights (replaced wholesale each release, not accumulated) — bump `CURRENT_WHATS_NEW_VERSION` (a date string) alongside it whenever you update the list, since that's what gates the auto-shown "What's new" modal (`WhatsNewModal.tsx`) for users who haven't seen the current version yet.
